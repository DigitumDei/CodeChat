# Query Response Shape

The `/query` endpoint supports both synchronous and streaming replies. Regardless of
mode, **successful** responses surface only the assistant text generated by the
selected provider—never any of the internal routing metadata. Non-success cases use a
consistent error envelope, with a few caveats called out below for streaming clients.

## Synchronous (`stream=false`, default)

A normal request returns an HTTP 200 with a UTF-8 encoded string body containing the
assistant's full reply:

```http
HTTP/1.1 200 OK
Content-Type: application/json

"Hello from CodeChat"
```

When `tools=true` is supplied, the server may execute functions and then still return
the final assistant text using the same plain-string shape once the tool loop
completes.

## Streaming (`stream=true`)

When streaming is enabled the response uses `text/event-stream`. The daemon strips the
provider's internal JSON frames and emits only the text token in each event so
clients should concatenate the event `data` values exactly as they arrive.

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream

retry: 15000

data: Hel


data: lo from


data:  CodeChat


```

The stream terminates naturally when the provider signals completion. When
`tools=true`, tool execution output is interleaved as additional text chunks before
stream completion. When the response is complete the daemon emits a final empty token
(`data:` with no payload) and then closes the connection.

Validation errors (for example, malformed request bodies) are returned before
streaming begins, so the client still receives the standard JSON envelope. Once the
event stream has started the daemon does **not** translate errors into JSON; instead,
it closes the connection after any partial tokens already sent. Clients should treat
an unexpected disconnect as an error condition and recover accordingly.

## Error responses

All errors follow a consistent JSON envelope regardless of transport mode. The HTTP
status communicates coarse failure type while the payload exposes a stable `code` and
message string.

```json
{
  "error": {
    "code": "INVALID_PROVIDER_RESPONSE",
    "msg": "Provider response missing 'text' field"
  }
}
```

Common error codes include:

- `VALIDATION_ERR` – request body failed FastAPI / Pydantic validation (HTTP 422)
- `HTTP_ERROR` – explicit `HTTPException` from request processing (status varies)
- `INVALID_PROVIDER_RESPONSE` – provider result omitted the required `text` field (HTTP 500)
- `UNEXPECTED_ERR` – unhandled server-side exception (HTTP 500)
